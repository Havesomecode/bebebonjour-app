## Routing and message format

Accept only authenticated Resend `email.received` events. Verify the bounded, unmodified UTF-8 request with the pinned Resend6.20.0 SDK's `webhooks.verify`, including Svix ID, timestamp, rotating signatures and five-minute tolerance, before interpreting or persisting event data. Verification and classification happen inside the HTTP isolate; only event/email IDs, SHA256 and a fixed disposition cross into the internal Node action. Raw payload, signature, sender, addresses and subject are not internal function arguments. Limit body to 64KiB, reject compression/non-JSON/malformed UTF-8 and bound all signature headers. Invalid signatures/formats return400; overflow413; unavailable/disabled configuration503. Responses contain fixed status codes only and are private/no-store. No payload/error logging is added.

Route only the exact receiving envelope `received_for: ["contact@bebebonjour.com"]` (ASCII case-insensitive), not user-controlled display `to`, cc/bcc or plus-address aliases. A missing envelope is invalid; a different/multiple envelope is ignored. Ignore senders `contact@bebebonjour.com`, `z@havesomecode.io` and `bonjour@updates.bebebonjour.com`, including display-name forms, to break return/forward loops. Destination is always `z@havesomecode.io`; sender is the existing verified-domain default `Bébé Bonjour <bonjour@updates.bebebonjour.com>`. Neither can be selected by webhook fields or configuration.

Call the documented SDK `emails.receiving.forward` with `passthrough:false`, fixed French text and a stable `support-forward:<email_id>` idempotency key. This SDK mode sends an attached `forwarded_message.eml`, preserving the original MIME message, sender/reply headers and attachments; the outer subject is the SDK's Fwd subject. Original content is not interpolated into outer HTML. Reply using the original attached message, not the forwarding sender. Receiving content/download URLs exist only inside the SDK invocation, never in the application's database or output.

## Durable effect fence and failure handling

Add only `supportForwardReceipts`, indexed by Svix event ID and inbound email ID. Internal-only mutations atomically create an `inflight` receipt before invoking the SDK. Store provider identifiers, raw-body SHA256, status, fixed reason and timestamps only. No subject, address list, sender, body, attachment metadata, raw MIME or signed URL is retained. Ignored valid events have an identifier-only terminal receipt. The other tables are untouched.

Concurrent/replayed events for the same inbound ID converge on one receipt and cannot issue a second forward, even with a new Svix ID. Same event/email identity with conflicting bytes is refused. On SDK acceptance record the outbound message ID as `sent`; this is provider acceptance, not inbox delivery. SDK error, timeout, missing acceptance ID or commit ambiguity returns503. An already `inflight` or `reconciliation_required` receipt always returns503 without another SDK call, including after the provider's 24-hour idempotency retention. No automatic lease reclaim, retry send, reset or public reconciliation API exists. Process interruption after the durable fence deliberately leaves `inflight`.

An authorized operator must inspect the exact inbound/outbound provider correlation before resolving an uncertain receipt. Never delete/reset the fence or resend merely because Resend retries. Ordinary transient failure before the fence can be retried; conservative failures after the fence require reconciliation even when they occurred during the SDK's initial reads. Ledger growth is per authenticated inbound event; disabling forwarding stops new application effects. This is not an anti-spam service or a guarantee of inbox delivery.
