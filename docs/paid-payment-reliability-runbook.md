## Receipt interpretation and reconciliation

HTTP200 means only a durably recorded disposition: `settled`, `test_only`, or `rejected`. It does not mean final delivery, human review, refund or inbox receipt.400 means signature/format rejection;413 means oversized bytes;503 means inspection/configuration/datastore uncertainty with no acknowledged new settlement receipt. Preserve exact event body bytes on redelivery; a fresh valid Stripe signature timestamp is allowed. Do not log raw bodies or use archived sensitive payloads as evidence.

1. On a503, inspect deployment configuration and bounded provider health/permission failures without exposing secrets. Repair only the exact cause. Permit the provider to redeliver the same event through the normal signed endpoint; no ledger edits, new job, new event identity, synthetic settlement or repeated final effect.
2. On an uncertain/lost HTTP response, query the immutable event identity and fingerprint plus existing payment evidence before taking any action. If committed, exact replay is a no-op, including after cancellation/deletion. If not committed, normal signed delivery safely retries. Do not infer receipt absence from an unavailable datastore.
3. For a durable `rejected`, privately inspect its allowlisted reason. Same identity/different bytes is a conflict; retain both immutable receipts. Wrong account/mode/amount/currency/job/revision/digest, withdrawn approval, expired/deleted/cancelled order or a PaymentIntent bound elsewhere must not advance authority. Do not repair by editing provider metadata to move paid authority to another job.
4. After separately resolving an eligible rejected scope, genuine current provider inspection is available through `/delivery/operator`, action `reconcile_payment`. Use the existing human-only editorial capability with exact `jobId`, `expectedRevision` and `providerPaymentId`. Read the private current state first. The rejected event receipt stays rejected; this action uses the same deduplicated payment evidence rather than a second entitlement. Cancelled/expired/deleted scope is not made eligible by reconciliation.
5. Final narration/publication/email require the independently authenticated human review and current consent fences. An `inflight`/uncertain narration or email fence requires exact effect reconciliation; never clear it or resend merely because payment is present. This endpoint is not a refund/dispute monitor: settled evidence is a verified observation at ingest time, not proof of future provider state.

The existing operator sends `POST /delivery/operator` with the private capability in `Authorization: Bearer <editorial capability>`, never a URL or browser storage. Request bodies (placeholders are not executable values):

```json
{"action":"read","jobId":"<exact-job-id>"}
{"action":"cancel","jobId":"<exact-job-id>","expectedRevision":1}
{"action":"reconcile_payment","jobId":"<exact-job-id>","expectedRevision":1,"providerPaymentId":"<exact-pi-id>"}
```

Read and use the actual current revision; `1` above is only the offline fixture example. The operator UI is the preferred credential ingress. Keep returned private preview/payment identifiers out of shared evidence. An operator cancellation is idempotent at the exact revision and has no implicit refund action.

## Rollback and separately authorized refund/dispute procedure

1. Close new paid preview admission (`BEBEBONJOUR_PAID_ROUTE_A_ENABLED=false`) and stop independently operated external collection. Neither action cancels existing obligations. Preserve the signed webhook route and current datastore; do not roll back to code without the receipt ledger or restore an old snapshot that loses deduplication/tombstones. Do not disable unrelated complimentary work or independently needed privacy controls.
2. If an existing order must be frozen, use authenticated operator `cancel` with its exact current revision before any provider remediation. Read back `cancelled`, unchanged financial evidence and retained uncertain-effect fences. Verify no final claim, private preview or public announcement is available. New late succeeded events reject as `order_cancelled`; exact earlier settled events return their historical disposition but do not touch the frozen job. Disabling admission alone intentionally allows a valid old obligation to settle; cancellation is the separate authority-revocation step.
3. With explicit current authorization for the exact refund/dispute action, the authorized payment operator verifies configured account/mode, the PaymentIntent/latest charge, already issued refunds/disputes and order/effect state. The human editorial capability grants application supervision only, not Stripe refund authority. The commercial decision packet supplies refund eligibility/amount/tax treatment; do not guess full/partial refund or currency, and never treat cancellation as proof of money returned.
4. Perform the authorized provider remediation once via the existing Stripe operator workflow. For an authorized CLI refund, the draft shape is `stripe refunds create --payment-intent <exact-pi-id> --amount <approved-minor-units> --idempotency-key <stable-order-refund-operation-id>` using the established secret mechanism, not a literal credential. The live/test invocation and exact approved arguments belong to downstream configuration/authorization, not this offline run. Read back the exact provider refund ID/status/amount/currency/account/payment binding before recording success. Pending/failed/uncertain refund is not a successful refund and is not blindly reissued under a new key.
5. Keep the order frozen. Retain minimal separate financial and effect evidence under [paid-route-a-data-controls.md](paid-route-a-data-controls.md); customer content erasure must not erase replay protection. New inspection rejects known refunded/disputed charges. Preserve uncertain effects and reconcile them explicitly. Reopening admission never reopens a cancelled order; no signed succeeded replay can unfreeze it.
