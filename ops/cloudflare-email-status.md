# Cloudflare email status boundary

Cloudflare's [`emailSendingAdaptive` analytics dataset](https://developers.cloudflare.com/analytics/graphql-api/sampling/) can be sampled and is not proof of the last event for a particular message. Until an exhaustive, timely per-message status source is qualified, automatic Cloudflare status inspection returns `cloudflare_status_unavailable`. A queued or sent receipt must not be promoted to delivered or failed from sampled analytics, and a started effect must not be resent merely because its status is unavailable. This limitation does not change historical Resend receipt inspection or incoming support routing.

The [structured REST send response reference](https://developers.cloudflare.com/api/resources/email_sending/) is distinct from the Workers binding: the Cloudflare API reference documents `message_id` and the recipient groups `delivered`, `queued`, `permanent_bounces`, and `suppressed_recipients`. The [REST guide](https://developers.cloudflare.com/email-service/api/send-emails/rest-api/) example omits `message_id`, while the generated API reference includes it. An observed send response or a synthetic fixture is not proof of inbox receipt. Qualify the real response and delivery before activation.
